> **Chapter 15** trong series **Playwright + TypeScript: Nguyen's Handbook**.

Viết test đã khó, nhưng phần lớn thời gian là *debug test fail*. Chapter này là bộ đồ nghề debug: chạy từng bước, xem trình duyệt thật, và đặc biệt là **Trace Viewer** - công cụ mình nghĩ mọi người nên dùng như phản xạ.

## 1. Debug Mode

```bash
# Chạy ở chế độ debug
npx playwright test --debug

# Debug riêng một test
npx playwright test login.spec.ts --debug
```

```ts
// Hoặc chèn dòng này vào test để dừng tại đó
await page.pause();
```

**Giải thích:**

- `--debug` mở **Playwright Inspector**: test chạy từng bước, bạn bấm "Next" để đi từng action, xem locator nào đang được chọn (highlight trên trang), chỉnh sửa locator trực tiếp.
- `await page.pause()` - đặt một "điểm dừng" ngay trong code. Khi chạy tới đây test dừng lại, mở Inspector để bạn thử nghiệm. Rất tiện khi muốn dừng đúng một chỗ cụ thể giữa test.

## 2. Headed Mode - xem trình duyệt thật

```bash
# Hiện cửa sổ trình duyệt khi chạy
npx playwright test --headed

# Chạy chậm lại để mắt theo kịp
npx playwright test --headed --slow-mo=1000
```

**Giải thích:**

- `--headed` - hiện trình duyệt ra (mặc định chạy ngầm/headless). Bạn thấy tận mắt test đang làm gì.
- `--slow-mo=1000` - làm chậm mỗi action 1000ms (1 giây). Khi test chạy quá nhanh không kịp nhìn, cái này giúp bạn quan sát từng bước. Chỉ dùng để debug, không bao giờ để trong CI.

## 3. Trace Viewer - vũ khí debug mạnh nhất

```ts
// playwright.config.ts
use: {
  trace: 'on-first-retry',     // ghi trace ở lần retry đầu
  screenshot: 'only-on-failure',
  video: 'retain-on-failure',  // giữ video khi fail
}
```

```bash
# Mở file trace để xem
npx playwright show-trace trace.zip
```

**Giải thích - vì sao Trace Viewer đáng giá:**

- **Trace** là một bản ghi *toàn diện* của lần chạy test: từng action, ảnh chụp DOM tại mỗi bước, request mạng, log console, thời gian... tất cả trong một file `.zip`.
- `trace: 'on-first-retry'` - chỉ ghi khi test fail và retry (không làm chậm các test pass).
- `npx playwright show-trace trace.zip` mở một giao diện cho bạn **"tua lại"** toàn bộ test: kéo thanh thời gian, xem trang trông thế nào *tại chính khoảnh khắc* một action chạy, soi network, console...
- Điểm hay nhất: bạn debug được test flaky **mà không cần chạy lại**. Một test thỉnh thoảng fail trên CI lúc 3 giờ sáng - bạn chỉ cần tải file trace về và xem lại đúng lần fail đó. Đây là thứ thay đổi hoàn toàn cách debug so với "thêm console.log rồi chạy lại 50 lần".

## 4. Debug ở mức chi tiết hơn

**Debug network:**

```ts
page.on('request', request => {
  console.log('→', request.method(), request.url());
});
page.on('response', response => {
  console.log('←', response.status(), response.url());
});
page.on('requestfailed', request => {
  console.log('✗', request.url(), request.failure()?.errorText);
});
```

**Giải thích:**

- `page.on('event', handler)` - đăng ký lắng nghe sự kiện trên page. Đây là cơ chế event-driven: mỗi khi sự kiện xảy ra, handler được gọi.
- `'request'` bắn mỗi khi có request đi ra; `'response'` mỗi khi có response về; `'requestfailed'` khi request thất bại.
- `request.failure()?.errorText` - lý do thất bại. `?.` (optional chaining) tránh crash nếu `failure()` trả `null`.
- Bộ ba này in ra toàn bộ "giao thông mạng" của trang - cực hữu ích khi nghi test fail do một API call lỗi/chậm.

**Debug console:**

```ts
page.on('console', msg => {
  console.log('Browser console:', msg.text());
});
page.on('pageerror', error => {
  console.log('Page error:', error.message);
});
```

- `'console'` - chuyển mọi `console.log` *bên trong trang web* ra terminal của test. Giúp thấy log của chính ứng dụng.
- `'pageerror'` - bắt lỗi JavaScript chưa được xử lý trong trang. Nếu app văng lỗi JS, đây là chỗ bạn thấy nó.

**Debug phần tử:**

```ts
// Đếm số phần tử khớp
const count = await button.count();
console.log(`Found ${count} elements`);

// Tô sáng phần tử (khi chạy headed)
await button.highlight();

// Lấy thông tin vị trí/kích thước
const box = await button.boundingBox();
console.log('Element position:', box);
```

- `.count()` - kiểm tra locator có khớp đúng số phần tử mong đợi không. Locator khớp 0 hoặc khớp quá nhiều phần tử là nguyên nhân fail rất phổ biến.
- `.highlight()` - vẽ khung quanh phần tử (chỉ thấy ở chế độ headed). Xác nhận locator đang trỏ đúng chỗ.
- `.boundingBox()` - trả về tọa độ và kích thước. Hữu ích khi debug vấn đề về layout/vị trí.

## 5. Các lỗi thường gặp & cách xử lý

**Timeout:**

```ts
// Tăng timeout cho cả test
test.setTimeout(120000); // 2 phút

// Tăng timeout cho một action cụ thể
await page.getByRole('button').click({ timeout: 60000 });
```

**Test flaky (lúc pass lúc fail):**

```ts
// ❌ Tệ - chờ một khoảng thời gian cứng
await page.waitForTimeout(3000);

// ✅ Tốt - chờ một điều kiện cụ thể
await page.waitForLoadState('networkidle');
await page.waitForSelector('.loaded');
await page.getByText('Success').waitFor();
```

**Giải thích - đây là bài học quan trọng nhất về chống flaky:**

- `waitForTimeout(3000)` là **anti-pattern**. Nó vừa làm test chậm (luôn đợi đủ 3s kể cả khi trang đã sẵn sàng sau 0.2s), vừa flaky (nếu mạng chậm hơn 3s thì vẫn fail). Tránh tối đa.
- Thay vào đó, đợi *điều kiện cụ thể*:
    - `waitForLoadState('networkidle')` - đợi tới khi không còn request mạng nào hoạt động.
    - `waitForSelector('.loaded')` - đợi tới khi phần tử có class `.loaded` xuất hiện.
    - `.waitFor()` - đợi locator cụ thể xuất hiện.
- Nguyên tắc: **đợi một sự kiện, đừng đợi một con số thời gian.** Đây cũng là tinh thần auto-wait đã nói từ Chapter 1.

**Chụp màn hình để debug:**

```ts
// Chụp full trang
await page.screenshot({ path: 'debug.png', fullPage: true });

// Chụp một phần tử
await page.locator('.error').screenshot({ path: 'error.png' });
```

> **Khuyến nghị:** Bật `trace: 'on-first-retry'` trong config. Bạn có đủ thông tin chi tiết để debug khi fail mà không làm chậm các lần chạy thành công. Nếu mình chỉ được giữ một mẹo debug duy nhất trong Playwright, đó là Trace Viewer.
