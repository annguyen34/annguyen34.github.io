> **Chapter 11** trong series **Playwright + TypeScript: Nguyen's Handbook**.

Hai mảng test này hay bị bỏ quên nhưng cực kỳ giá trị: **visual regression** bắt được những lỗi giao diện mà assertion text bỏ sót (layout vỡ, màu sai, font lệch), còn **accessibility** đảm bảo app dùng được cho mọi người - và với nhiều ngành (ngân hàng, chính phủ) còn là yêu cầu pháp lý.

## 1. Visual Regression Testing

Ý tưởng: chụp ảnh "chuẩn" (baseline) một lần, các lần sau so sánh ảnh mới với baseline. Nếu khác → có thể UI đã vỡ.

**So sánh ảnh cơ bản:**

```ts
test('homepage visual test', async ({ page }) => {
  await page.goto('/');
  await expect(page).toHaveScreenshot('homepage.png');
});
```

`toHaveScreenshot('homepage.png')` - lần chạy **đầu tiên** tạo baseline tên `homepage.png`. Các lần sau, Playwright chụp lại và so pixel-by-pixel với baseline. Nếu khác quá ngưỡng → test fail và sinh ảnh diff cho bạn xem chỗ khác.

**Chụp một phần tử:**

```ts
test('header visual test', async ({ page }) => {
  await page.goto('/');
  const header = page.locator('header');
  await expect(header).toHaveScreenshot('header.png');
});
```

Thay vì cả trang, chỉ chụp riêng `<header>`. Hữu ích khi bạn chỉ quan tâm một component và không muốn phần còn lại của trang gây nhiễu.

**Chụp full trang:**

```ts
test('full page screenshot', async ({ page }) => {
  await page.goto('/pricing');
  await expect(page).toHaveScreenshot('pricing-page.png', { fullPage: true });
});
```

`fullPage: true` - chụp toàn bộ trang kể cả phần phải cuộn xuống mới thấy, không chỉ phần trong viewport.

**Config nâng cao - xử lý nội dung động:**

```ts
test('dashboard with masking', async ({ page }) => {
  await page.goto('/dashboard');

  await expect(page).toHaveScreenshot('dashboard.png', {
    maxDiffPixels: 100,        // cho phép lệch tối đa 100 pixel
    threshold: 0.2,            // ngưỡng khác biệt màu 20%
    mask: [                    // che các vùng nội dung động
      page.locator('.timestamp'),
      page.locator('.balance'),
    ],
    animations: 'disabled',    // tắt animation khi chụp
  });
});
```

**Giải thích - đây là chỗ visual test hay "flaky" nếu không cấu hình đúng:**

- `maxDiffPixels: 100` - cho phép tối đa 100 pixel khác biệt mà vẫn coi là pass. Giúp bỏ qua sai lệch render cực nhỏ giữa các máy.
- `threshold: 0.2` - ngưỡng nhạy về *màu sắc* cho mỗi pixel (0 = cực gắt, 1 = lỏng). 0.2 là mức cân bằng phổ biến.
- `mask: [...]` - **quan trọng nhất.** Đây là danh sách các vùng *luôn thay đổi* (đồng hồ thời gian, số dư, quảng cáo...). Playwright sẽ phủ một lớp lên chúng khi so sánh, để chúng không làm test fail oan. Không có `mask`, một cái timestamp đổi mỗi giây sẽ khiến test fail mãi mãi.
- `animations: 'disabled'` - tắt CSS animation/transition khi chụp, tránh việc chụp đúng lúc đang animate dở dang gây ảnh khác nhau.

**Visual test responsive (nhiều kích thước màn hình):**

```ts
const viewports = [
  { name: 'mobile',  width: 375,  height: 667  },
  { name: 'tablet',  width: 768,  height: 1024 },
  { name: 'desktop', width: 1920, height: 1080 },
];

for (const viewport of viewports) {
  test(`visual test - ${viewport.name}`, async ({ page }) => {
    await page.setViewportSize(viewport);
    await page.goto('/');
    await expect(page).toHaveScreenshot(`page-${viewport.name}.png`);
  });
}
```

**Giải thích:**

- Đây là **data-driven testing**: ta lặp qua mảng `viewports`, mỗi vòng tạo một test riêng. Vòng lặp `for` đặt *ngoài* `test()` để sinh ra nhiều test case độc lập (mobile/tablet/desktop), thay vì gộp vào một test.
- `page.setViewportSize(viewport)` - đặt kích thước màn hình giả lập trước khi chụp.
- `toHaveScreenshot('page-${viewport.name}.png')` - tên baseline động theo từng viewport (dùng template string backtick), nên mỗi kích thước có ảnh chuẩn riêng.

**Cập nhật baseline:**

```bash
# Cập nhật tất cả ảnh chuẩn
npx playwright test --update-snapshots

# Cập nhật riêng một file test
npx playwright test homepage.spec.ts --update-snapshots
```

Khi bạn *cố ý* đổi UI, baseline cũ sẽ fail - đúng như mong đợi. Sau khi xác nhận giao diện mới đúng, chạy `--update-snapshots` để ghi đè baseline mới.

## 2. Accessibility Testing với axe-core

`axe-core` là thư viện kiểm tra accessibility hàng đầu, tích hợp gọn vào Playwright.

**Cài đặt:**

```bash
npm install -D @axe-core/playwright
```

**Test accessibility cơ bản:**

```ts
import { test, expect } from '@playwright/test';
import AxeBuilder from '@axe-core/playwright';

test('homepage accessibility', async ({ page }) => {
  await page.goto('/');

  const accessibilityScanResults = await new AxeBuilder({ page }).analyze();

  expect(accessibilityScanResults.violations).toEqual([]);
});
```

**Giải thích:**

- `import AxeBuilder from '@axe-core/playwright'` - import bộ quét.
- `new AxeBuilder({ page }).analyze()` - quét trang hiện tại tìm vi phạm accessibility. Trả về object kết quả, trong đó `violations` là mảng các lỗi tìm thấy.
- `expect(violations).toEqual([])` - khẳng định **không có** vi phạm nào (mảng rỗng). `toEqual` so sánh sâu giá trị (khác `toBe` so sánh tham chiếu) - phù hợp khi so sánh mảng/object.

**Kiểm tra theo tiêu chuẩn WCAG cụ thể:**

```ts
test('banking form accessibility', async ({ page }) => {
  await page.goto('/transfer');

  const results = await new AxeBuilder({ page })
    .withTags(['wcag2a', 'wcag2aa', 'wcag21aa'])
    .analyze();

  if (results.violations.length > 0) {
    console.log('Accessibility Violations:');
    results.violations.forEach(violation => {
      console.log(`- ${violation.description}`);
      console.log(`  Impact: ${violation.impact}`);
      console.log(`  Elements: ${violation.nodes.length}`);
    });
  }

  expect(results.violations).toEqual([]);
});
```

**Giải thích:**

- `.withTags(['wcag2a', 'wcag2aa', 'wcag21aa'])` - giới hạn quét theo các mức tiêu chuẩn WCAG (A, AA, và WCAG 2.1 AA). Nhờ đó bạn tập trung đúng mức tuân thủ mình cần.
- Khối `if (violations.length > 0)` - nếu có lỗi, in chi tiết ra console: mô tả, mức độ ảnh hưởng (`impact`), và số phần tử dính lỗi (`violation.nodes.length`). Giúp bạn debug nhanh thay vì chỉ thấy "fail".
- `.forEach(...)` - duyệt qua từng vi phạm để in.

**Các tiêu chí WCAG quan trọng** (tham khảo): 1.1.1 Text Alternatives (A), 1.3.1 Info & Relationships (A), 1.4.3 Contrast tối thiểu (AA), 2.1.1 Keyboard (A), 2.4.7 Focus Visible (AA), 3.3.2 Labels or Instructions (A).

**Loại trừ vùng đã biết có vấn đề:**

```ts
test('accessibility with exclusions', async ({ page }) => {
  await page.goto('/');

  const results = await new AxeBuilder({ page })
    .exclude('.third-party-widget')   // bỏ qua widget bên thứ ba
    .disableRules(['color-contrast']) // tạm tắt một rule
    .analyze();

  expect(results.violations).toEqual([]);
});
```

**Giải thích:**

- `.exclude('.third-party-widget')` - loại một vùng khỏi phạm vi quét. Thường dùng cho widget của bên thứ ba mà bạn không kiểm soát được mã nguồn.
- `.disableRules(['color-contrast'])` - tạm tắt một rule cụ thể. Dùng *thận trọng* và nên kèm ghi chú lý do - đây nên là giải pháp tạm thời, không phải cách che giấu lỗi vĩnh viễn.

> **Thực tế:** Nhiều tổ chức (đặc biệt ngân hàng, dịch vụ công) bắt buộc tuân thủ WCAG. Chạy accessibility test trong CI/CD giúp chặn vi phạm trước khi lên production. Nhưng cũng nên nhớ: axe-core bắt được phần lớn lỗi *tự động phát hiện được*, không thay thế hoàn toàn việc kiểm tra thủ công bằng screen reader.
